# 2.6.1 Redesign — Pelecard Billing Atomicity

> **מטרה:** עיצוב מחדש של זרימת הסליקה בפלאקארד, כדי לפתור 2 שורשים מבניים שגרמו לרצף של 9 סבבי תיקון לא-יעילים.
>
> **קלט יחיד ל-Claude Code.** כל שינוי קוד יבוצע לפי מסמך זה. אין "תקן את X" — רק "יישם את הקובץ הזה."
>
> **Baseline:** `080d2ee` (סוף סבב 4). סבבים 5-9 הוסרו מההיסטוריה.
>
> **גרסה:** v2 — כולל את התיקונים מהדיון בצ'אט אחרי שגרסת v1 פורסמה. ראה §9 (Changelog) בסוף.

## 1. בעיה ומטרה

### הסבבים שעשו את זה לכאן

PR 2.6.1 עבר 9 סבבי Bugbot. 3 באגים נוספים התגלו אחרי סבב 9. המפה של CC (5 בקשות חקירה) הצביעה על שני שורשים מבניים, לא נקודתיים.

### שורש A — אסימטריה בין webhook לפונקציות חיוב

ה-webhook קיבל RPC אטומי שפתר 4 פגמים בעת ובעונה אחת:
- חיוב חיצוני בלתי-הפיך לפני state-change
- `rowcount` לא נבדק
- אין idempotency key
- אין reconciliation logging

**שלוש פונקציות החיוב** (`charge_trial_end`, `charge_monthly`, `charge_past_due`) **לא קיבלו את אותו טיפול.** הן עדיין סובלות מאותם 4 פגמים.

**ועוד:** אחרי ה-reset ל-`080d2ee`, ה-webhook עצמו **חזר להיות לא-אטומי** (סבב 9 שתיקן אותו נמחק). הוא דורש שחזור עם דפוס דומה — ראה רכיב 5 ב-§2.

### שורש B — "גישה" מוגדרת פעמיים, סותרת

- `has_active_billing` (computed) → מתעלם מ-grace period.
- `is_locked` (computed) → מיישם grace period.
- 5 הגדרות inline נוספות של "מצב פעיל" מפוזרות בקוד.

**התוצאה:** משתמש שביטל ובתוך grace רואה את ה-UI פתוח (`is_locked=False`), אבל פעולות חסומות (`has_active_billing=False`). סתירה.

### האילוץ שגילינו

ה-migrations הם **append-only בפועל** (`migrate.py` עוקב לפי filename, לא hash). כל תיקון שורש = migration חדש קדימה.

### מה פלאקארד דורשת מאיתנו

מהתשובה הרשמית של פלאקארד:

1. **אין idempotency-key מובנה.** distributed lock מצידנו, חובה.
2. **`PelecardTransactionId` הוא מפתח deduplication אמין** — לא `ParamX`.
3. **`PelecardStatusCode='000'` הוא היחיד שאומר "הצליח".** כל דבר אחר = פעולה לא-הסתיימה.
4. **חלון 30 דקות לפני סימון "נטוש".**

## 2. העיצוב המוצע — 5 רכיבים

### רכיב 1: state `charging` כ-state ביניים מפורש

**הגדרה:** state חדש ב-enum `subscriptions.status`, שמייצג "ניסיון חיוב בעיצומו". worker יחיד יכול להחזיק אותו בכל רגע.

**המעברים החוקיים החדשים:**

```
trial    → charging → active     (חיוב יום 8 הצליח)
trial    → charging → past_due   (חיוב יום 8 נכשל)
active   → charging → active     (חיוב חודשי הצליח, period קודם)
active   → charging → past_due   (חיוב חודשי נכשל)
past_due → charging → active     (retry הצליח)
past_due → charging → expired    (כל ה-retries נכשלו)
charging → <כל ה-states הקודמים>  (cleanup cron — ראה רכיב 3)
```

**הזרימה החדשה בכל פונקציית חיוב:**

```
1. cron בוחר user לפי תנאי סינון (status='trial' AND trial_ends_at<now וכו')
2. CAS אטומי:
   UPDATE subscriptions SET status='charging'
   WHERE user_id=? AND status=<התנאי המקורי>
   RETURNING <fields>
   → בדיקת rowcount=1. אם 0 → worker שני תפס, יציאה שקטה.
3. INSERT ל-billing_charge_attempts (ראה רכיב 2) עם idempotency_key.
   → אם כבר קיים (UNIQUE violation) → טיפול ספציפי (כנראה reuse).
4. קריאה לפלאקארד charge_token.
5. RPC אטומי:
   - UPDATE billing_charge_attempts עם התוצאה (status, pelecard_transaction_id, debit_total).
   - UPDATE subscriptions ל-state הסופי (active/past_due/expired).
   - שני ה-UPDATEs בטרנזקציה אחת.
```

**המפתח:** שני workers לא יכולים לעבור ביחד את שלב 2. רק אחד יקבל `charging`, השני יקבל `rowcount=0` ויסיים.

### רכיב 2: טבלה חדשה `billing_charge_attempts`

**מטרה:**
- idempotency-key מצידנו (פלאקארד לא תומכת).
- היסטוריית ניסיונות שמירת `pelecard_transaction_id` עוד **לפני** התשובה (חיוני ל-cleanup cron).
- reconciliation logging.

**הסכמה:**

```sql
CREATE TABLE billing_charge_attempts (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  subscription_id uuid NOT NULL REFERENCES subscriptions(id) ON DELETE CASCADE,
  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,

  -- idempotency: unique per (subscription, period, attempt_type)
  attempt_type text NOT NULL CHECK (attempt_type IN ('trial_end', 'monthly', 'past_due_retry')),
  period_anchor timestamptz NOT NULL,  -- current_period_start בעת הניסיון
  idempotency_key text NOT NULL,  -- generated: f"{subscription_id}:{attempt_type}:{period_anchor.isoformat()}"

  -- Pelecard data (nullable - נכתב כשיש)
  pelecard_transaction_id text,
  pelecard_status_code text,
  debit_total_agorot integer,
  amount_charged_ils numeric(10, 2),

  -- attempt lifecycle
  status text NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'succeeded', 'failed', 'unknown')),
  started_at timestamptz NOT NULL DEFAULT now(),
  completed_at timestamptz,
  error_message text,

  -- audit
  created_at timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT unique_idempotency UNIQUE (idempotency_key)
);

CREATE INDEX idx_charge_attempts_user ON billing_charge_attempts(user_id, started_at DESC);
CREATE INDEX idx_charge_attempts_pending ON billing_charge_attempts(status, started_at)
  WHERE status = 'pending';
```

**RLS:**
- SELECT למשתמש על שלו (`auth.uid() = user_id`).
- INSERT/UPDATE/DELETE רק דרך admin client (services, לא קליינט).

### רכיב 3: cleanup cron ל-`charging` תקועים

**מטרה:** אם worker קרס בין שלב 2 (CAS) לשלב 5 (RPC סופי) — שורה נתקעת ב-`charging`. צריך cron נפרד שמנקה.

**הזרימה:**

```python
# רץ כל 30 שניות
def cleanup_stuck_charging():
    rows = SELECT s.id, s.user_id, s.status, bca.id as attempt_id,
                  bca.pelecard_transaction_id
           FROM subscriptions s
           JOIN billing_charge_attempts bca
             ON bca.subscription_id = s.id AND bca.status = 'pending'
           WHERE s.status = 'charging'
             AND bca.started_at < now() - interval '3 minutes'

    for row in rows:
        if row.pelecard_transaction_id is None:
            # החיוב לא הגיע לפלאקארד (קריסה לפני שלב 4)
            → RPC: rollback to previous state + attempt='failed' (no charge attempted)
            continue

        # יש pelecard_transaction_id — צריך לבדוק אצל פלאקארד מה קרה
        result = pelecard.get_transaction(row.pelecard_transaction_id)

        if result.status_code == '000' and result.debit_total > 0:
            # פלאקארד אומרת שהחיוב הצליח
            → RPC: advance to next state + attempt='succeeded'
        elif result.status_code != '000':
            # פלאקארד אומרת שהחיוב נכשל
            → RPC: rollback to past_due + attempt='failed'
        else:
            # ambiguous (status_code='000' אבל debit_total=0?) — לא מצופה
            → RPC: status='unknown' + alert ל-Sentry
```

**timeout = 3 דקות.** חיוב פלאקארד אמיתי = 1-3 שניות. 3 דקות = buffer של פי 60-180. סביר.

**הערה חשובה:** ה-cleanup cron הוא **בעצמו פעולה אטומית.** הוא משתמש ב-CAS דומה:

```sql
UPDATE billing_charge_attempts
SET status = ?, completed_at = now()
WHERE id = ? AND status = 'pending'  -- CAS: רק אם עוד pending
```

אם cleanup cron אחר כבר נגע — `rowcount=0`, יוצאים בשקט.

### רכיב 4: `has_paid_access` יחיד שמחליף את שניהם

**מטרה:** מקור-אמת אחד למצב "האם המשתמש יכול להשתמש במוצר."

**ההגדרה:**

```python
@computed_field
def has_paid_access(self) -> bool:
    """
    The single source of truth for 'user can use the product'.
    Replaces: is_locked (inverted), has_active_billing.
    """
    # מנוי פעיל בכל המצבים האלה
    if self.status in ('trial', 'active', 'charging', 'past_due'):
        return True

    # ביטול בתוך grace period
    if self.status == 'canceled' and self.current_period_start:
        grace_end = add_one_month(self.current_period_start)
        if datetime.now(timezone.utc) < grace_end:
            return True

    return False
```

**שים לב:** משתמשים ב-`add_one_month` הקיים בקוד (`subscription_service.py`), **לא** ב-`dateutil.relativedelta`. סיבות:
1. הפונקציה קיימת ב-baseline (סבב 2/4) וכבר טופלו בה edge cases (30 ימים לא קלנדריים, פברואר).
2. ה-cron של חיובים חודשיים כבר משתמש בה — שני מקומות יחשבו "חודש קדימה" באותה דרך.
3. לא להוסיף תלות חיצונית כשפתרון פנימי קיים.

**מחיקות:**
- `is_locked` (computed_field) → מוחק.
- `has_active_billing` (computed_field + pure function) → מוחק את שניהם.
- 5 ההגדרות inline → מחליפים בקריאה ל-`has_paid_access`.

**שינויים בקוד שקורא להם:**
- כל מקום שהשתמש ב-`is_locked` → `not has_paid_access`.
- כל מקום שהשתמש ב-`has_active_billing` → `has_paid_access`.

### רכיב 5: שכבת אטומיות ל-webhook (`activate_trial_with_billing` RPC חדש)

**מטרה:** אחרי ה-reset ל-baseline, ה-webhook **חזר להיות לא-אטומי** (סבב 9 שתיקן אותו נמחק). יש לבנות RPC חדש שמשלב את האטומיות באותו דפוס של רכיב 1.

**הזרימה החדשה ב-webhook:**

```
1. אימות חתימת ה-webhook + idempotency דרך webhook_events.
2. RPC אטומי `activate_trial_with_billing`:
   - CAS על subscriptions עם guard
   - vault.create_secret עם billing_token
   - UPDATE subscriptions עם פרטי הכרטיס (card_last_four, expiry, trial_ends_at = now() + 7 days)
   - DELETE FROM pending_billing_sessions WHERE user_id = ?
   - הכל בטרנזקציה אחת
   - return: jsonb עם status
3. אם החזרה 'activated' → mark webhook_events as processed.
4. אם 'already_activated'/'state_mismatch' → log + return 200 ל-Pelecard (אל תעורר retry).
```

**ה-CAS guard:**

```sql
WHERE user_id = p_user_id
  AND status = 'trial'
  AND billing_customer_id IS NULL
FOR UPDATE;
```

**שני guards:**
- `status = 'trial'` → אם המנוי בוטל (cancel-race), `status='canceled'` → לא תופס. בטוח.
- `billing_customer_id IS NULL` → אם ה-webhook כבר רץ פעם אחת (re-entry / IPN כפול), `billing_customer_id` כבר נכתב → לא תופס. בטוח.

**שני אלה ביחד מבטיחים:** activation תקרה פעם אחת בדיוק, גם אם פלאקארד תשלח את ה-IPN פעמיים.

**ערכי החזרה (jsonb):**
- `{'status': 'activated'}` — הצליח, המנוי הופעל.
- `{'status': 'already_activated'}` — billing_customer_id כבר NOT NULL (re-entry).
- `{'status': 'state_mismatch'}` — status != 'trial' (למשל canceled).
- `{'status': 'no_subscription'}` — אין שורה בכלל לאותו user.

**הערה חשובה:** `trial_ends_at` הוא **תוצאה** של ה-webhook (`now() + 7 days`), **לא** precondition. ב-baseline הנוכחי `trial_ends_at` הוא NULL עד שה-webhook קובע אותו. לכן אסור להשתמש בו ב-CAS condition.

## 3. הרחבה ל-`start_trial_with_billing`

אותו דפוס reserve-before-fill חל גם פה. כיום:
```
1. create_validation_session בפלאקארד  ← side-effect חיצוני
2. upsert ל-pending_billing_sessions   ← אם נכשל, session יתום בפלאקארד
```

**הזרימה החדשה:**

```
1. INSERT INTO pending_billing_sessions (user_id, status='reserving')
   → אם UNIQUE violation על user_id (יש session פעיל) → 409 Conflict ללקוח.

2. קריאה לפלאקארד: create_validation_session.

3. UPDATE pending_billing_sessions
   SET status='reserved', pelecard_session_id=?, confirmation_key=?
   WHERE user_id=? AND status='reserving'.
   → rowcount=1 הכרחי. אחרת — cleanup.

4. החזרה ל-frontend: {iframe_url, confirmation_key}.
```

### עיצוב פשוט: בלי DROP UNIQUE, בלי partial index

**ה-UNIQUE המלא של 0006** (`pending_billing_sessions_user_id_key`) **נשאר כפי שהוא.** הוא הופך אוטומטית למנגנון "session פעיל אחד פר user."

**שורות `consumed`/`failed` נמחקות מיד, לא מצטברות:**
- אחרי `consumed` (ה-webhook הצליח להפעיל את ה-trial) → **DELETE FROM pending_billing_sessions WHERE user_id=?** ב-RPC `activate_trial_with_billing`.
- אחרי `failed` (cleanup cron מצא session תקוע ב-`reserving`) → **DELETE FROM pending_billing_sessions** ע"י ה-cleanup cron.

**יתרונות העיצוב:**
- אין שינוי לסכמה הקיימת של UNIQUE.
- אין partial index מסובך.
- אין שורות "מתות" שמצטברות.
- אם user רוצה session חדש אחרי שאחד הסתיים — אין שורה ישנה לחסום אותו (כי היא נמחקה).

**עמודת `status` ב-`pending_billing_sessions`:**
- מתווספת ב-Migration 0010.
- **רק 2 ערכים ב-CHECK:** `reserving`, `reserved`.
- terminal states (`consumed`, `failed`) **לא** נכנסים ל-CHECK כי שורות במצבים האלה נמחקות מיד.

### cleanup cron ל-`reserving` תקועים

**הזרימה:**

```python
# רץ כל 30 שניות
def cleanup_stuck_reserving():
    rows = SELECT id, user_id, pelecard_session_id
           FROM pending_billing_sessions
           WHERE status = 'reserving'
             AND created_at < now() - interval '2 minutes'

    for row in rows:
        # אופציונלי: לבדוק אצל פלאקארד אם session קיים
        # אבל בכל מקרה — מוחקים את השורה אצלנו.
        DELETE FROM pending_billing_sessions WHERE id = row.id
```

**timeout = 2 דקות** (פלאקארד session validation = שניות בודדות; 2 דקות = buffer גדול).

## 4. שינויי DB — Migrations

**Migration 0009 — atomic charge infrastructure:**

```sql
-- 0009_atomic_charging.sql

-- 1. הוספת 'charging' ל-status enum
ALTER TABLE subscriptions
  DROP CONSTRAINT IF EXISTS subscriptions_status_check;
ALTER TABLE subscriptions
  ADD CONSTRAINT subscriptions_status_check
    CHECK (status IN ('trial', 'active', 'charging',
                      'past_due', 'expired', 'canceled'));

-- ⚠️ שים לב: 'pending' לא ב-CHECK. הוא ערך של tier, לא של status.

-- 2. טבלת billing_charge_attempts (כפי שמוגדר ברכיב 2)
CREATE TABLE billing_charge_attempts (...);
ALTER TABLE billing_charge_attempts ENABLE ROW LEVEL SECURITY;
CREATE POLICY ... (SELECT לבעלים);

-- 3. RPC אטומי ליישוב ניסיון חיוב
CREATE OR REPLACE FUNCTION finalize_charge_attempt(
  p_attempt_id uuid,
  p_subscription_id uuid,
  p_pelecard_transaction_id text,
  p_pelecard_status_code text,
  p_debit_total_agorot integer,
  p_new_subscription_status text,
  p_new_current_period_start timestamptz DEFAULT NULL
) RETURNS jsonb
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ''  -- ⚠️ ריק, עם שמות מלאים בקוד (public.X, vault.X)
AS $$
DECLARE
  v_attempt_rowcount integer;
  v_sub_rowcount integer;
BEGIN
  -- שני UPDATEs בטרנזקציה אחת
  UPDATE public.billing_charge_attempts
  SET status = CASE
    WHEN p_pelecard_status_code = '000' THEN 'succeeded'
    ELSE 'failed'
  END,
  pelecard_transaction_id = p_pelecard_transaction_id,
  pelecard_status_code = p_pelecard_status_code,
  debit_total_agorot = p_debit_total_agorot,
  amount_charged_ils = p_debit_total_agorot / 100.0,
  completed_at = now()
  WHERE id = p_attempt_id AND status = 'pending';

  GET DIAGNOSTICS v_attempt_rowcount = ROW_COUNT;

  IF v_attempt_rowcount = 0 THEN
    RETURN jsonb_build_object('success', false, 'reason', 'attempt_already_finalized');
  END IF;

  UPDATE public.subscriptions
  SET status = p_new_subscription_status,
      current_period_start = COALESCE(p_new_current_period_start, current_period_start),
      updated_at = now()
  WHERE id = p_subscription_id AND status = 'charging';

  GET DIAGNOSTICS v_sub_rowcount = ROW_COUNT;

  IF v_sub_rowcount = 0 THEN
    RAISE EXCEPTION 'subscription not in charging state';
  END IF;

  RETURN jsonb_build_object('success', true);
END;
$$;

REVOKE EXECUTE ON FUNCTION finalize_charge_attempt FROM public;
GRANT EXECUTE ON FUNCTION finalize_charge_attempt TO service_role;

-- 4. RPC אטומי להפעלת trial (webhook activation)
CREATE OR REPLACE FUNCTION activate_trial_with_billing(
  p_user_id uuid,
  p_billing_token text,
  p_billing_customer_id text,
  p_card_last_four text,
  p_card_expiry text
) RETURNS jsonb
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ''
AS $$
DECLARE
  v_subscription record;
  v_secret_id uuid;
BEGIN
  -- CAS עם שני guards
  SELECT * INTO v_subscription
  FROM public.subscriptions
  WHERE user_id = p_user_id
    AND status = 'trial'
    AND billing_customer_id IS NULL
  FOR UPDATE;

  IF NOT FOUND THEN
    -- בדיקה: יש שורה אבל לא עומדת בתנאים?
    IF EXISTS (SELECT 1 FROM public.subscriptions
               WHERE user_id = p_user_id AND billing_customer_id IS NOT NULL) THEN
      RETURN jsonb_build_object('status', 'already_activated');
    END IF;

    IF EXISTS (SELECT 1 FROM public.subscriptions
               WHERE user_id = p_user_id AND status != 'trial') THEN
      RETURN jsonb_build_object('status', 'state_mismatch');
    END IF;

    RETURN jsonb_build_object('status', 'no_subscription');
  END IF;

  -- vault.create_secret לטוקן
  v_secret_id := vault.create_secret(p_billing_token, 'billing_token_' || p_user_id::text);

  -- UPDATE subscriptions
  -- ⚠️ תוקן: העמודה היא billing_token (0006), לא billing_token_secret_id.
  UPDATE public.subscriptions
  SET billing_token = v_secret_id,
      billing_customer_id = p_billing_customer_id,
      billing_card_last_four = p_card_last_four,
      billing_card_expiry = p_card_expiry,
      trial_ends_at = now() + interval '7 days',
      current_period_start = now(),
      updated_at = now()
  WHERE id = v_subscription.id;

  -- DELETE pending session (lifecycle ended)
  DELETE FROM public.pending_billing_sessions WHERE user_id = p_user_id;

  RETURN jsonb_build_object('status', 'activated');
END;
$$;

REVOKE EXECUTE ON FUNCTION activate_trial_with_billing FROM public;
GRANT EXECUTE ON FUNCTION activate_trial_with_billing TO service_role;
```

```python
async def charge_trial_end(subscription: Subscription) -> ChargeResult:
    """
    Atomic charging flow. See docs/2.6.1-redesign.md §2 רכיב 1.
    """
    # שלב 1: CAS to 'charging'
    cas_result = await db.execute("""
        UPDATE subscriptions
        SET status = 'charging', updated_at = now()
        WHERE id = $1 AND status = 'trial' AND trial_ends_at < now()
        RETURNING id, billing_token, tier
    """, subscription.id)

    if not cas_result:
        logger.info("charge_trial_end: CAS missed", subscription_id=subscription.id)
        return ChargeResult(status='skipped')

    # שלב 2: רישום attempt (idempotent)
    idempotency_key = f"{subscription.id}:trial_end:{subscription.current_period_start.isoformat()}"
    try:
        attempt = await db.execute("""
            INSERT INTO billing_charge_attempts
                (subscription_id, user_id, attempt_type, period_anchor, idempotency_key, status)
            VALUES ($1, $2, 'trial_end', $3, $4, 'pending')
            RETURNING id
        """, subscription.id, subscription.user_id,
             subscription.current_period_start, idempotency_key)
    except UniqueViolation:
        await db.execute("""
            UPDATE subscriptions SET status = 'trial'
            WHERE id = $1 AND status = 'charging'
        """, subscription.id)
        return ChargeResult(status='already_attempted')

    # שלב 3: קריאה לפלאקארד (חוץ מטרנזקציה!)
    try:
        pelecard_result = await pelecard.charge_token(
            token=await get_decrypted_token(subscription.user_id),
            amount_agorot=tier_to_amount(cas_result.tier) * 100,
            param_x=f"charge:{attempt.id}",
        )
    except Exception as e:
        logger.error("pelecard call failed", attempt_id=attempt.id, error=str(e))
        return ChargeResult(status='pelecard_error')

    # שלב 4: RPC אטומי לסיים
    rpc_result = await db.rpc('finalize_charge_attempt', {
        'p_attempt_id': attempt.id,
        'p_subscription_id': subscription.id,
        'p_pelecard_transaction_id': pelecard_result.transaction_id,
        'p_pelecard_status_code': pelecard_result.status_code,
        'p_debit_total_agorot': pelecard_result.debit_total,
        'p_new_subscription_status': 'active' if pelecard_result.is_success else 'past_due',
        'p_new_current_period_start': now() if pelecard_result.is_success else None,
    })

    if not rpc_result['success']:
        logger.warning("finalize_charge_attempt failed",
                       attempt_id=attempt.id, reason=rpc_result.get('reason'))
        return ChargeResult(status='finalize_failed')

    return ChargeResult(
        status='succeeded' if pelecard_result.is_success else 'failed',
        attempt_id=attempt.id,
    )
```

**הסבר על `param_x`:** משתמשים ב-`attempt.id` בתור `param_x`. ככה אם פלאקארד שולחת IPN על אותה עסקה — נוכל למצוא את ה-attempt בקלות.

## 6. תוכנית בדיקות

### בדיקות לכל אחד מ-2 השורשים:

**שורש A — אסימטריה פלאקארד/state:**

1. **CAS race:** שני workers מנסים `charge_trial_end` על אותו user במקביל → רק אחד עובר, השני יוצא נקי.
2. **פלאקארד הצליחה + DB UPDATE נכשל:** mock של `finalize_charge_attempt` שמחזיר failed → cleanup cron מטפל תוך 3 דקות.
3. **פלאקארד timeout:** mock של `charge_token` שזורק exception → attempt נשאר ב-pending, cleanup cron בודק אצל פלאקארד.
4. **כפילות:** מריצים `charge_trial_end` פעמיים עם אותו `period_anchor` → second call מקבל `already_attempted`, לא יוצרים חיוב שני.

**שורש B — `has_paid_access` יחיד:**

5. משתמש `canceled` בתוך grace → `has_paid_access=True`.
6. משתמש `canceled` אחרי grace → `has_paid_access=False`.
7. משתמש `charging` → `has_paid_access=True`.
8. אין סתירה בין שני computed fields (כי יש רק אחד).

### בדיקות לרכיב 3 (cleanup cron):

9. שורה ב-`charging` עם `started_at < 3 דקות` → לא נוגעים בה.
10. שורה ב-`charging` עם `started_at > 3 דקות` ובלי `pelecard_transaction_id` → חזרה ל-state המקורי.
11. שורה ב-`charging` עם `pelecard_transaction_id` ו-`get_transaction` מחזיר `status='000'` → קידום ל-active.
12. שורה ב-`charging` עם `pelecard_transaction_id` ו-`get_transaction` מחזיר `status<>'000'` → חזרה ל-past_due.

### בדיקות לרכיב 5 (webhook activation):

13. webhook מגיע לראשונה → `activate_trial_with_billing` מחזיר `'activated'`, trial_ends_at נקבע, pending_billing_sessions נמחק.
14. webhook מגיע פעמיים → השני מחזיר `'already_activated'`, אין שינוי כפול.
15. webhook מגיע אחרי cancel-race → מחזיר `'state_mismatch'`, אין activate.

### בדיקות שונות:

16. `start_trial_with_billing` — שתי בקשות סימולטניות מאותו user → רק אחת מצליחה, השנייה מקבלת 409 (UNIQUE violation).
17. Webhook מגיע ל-session ב-`reserving` (worker עוד לא הספיק לעדכן ל-`reserved`) → state_mismatch / המתנה.

- בדיקת migrations: 0009 + 0010 רצים נקי על DB ריק.

## 9. Changelog — תיקונים בין v1 ל-v2

מסמך זה (v2) הוא עדכון של גרסה ראשונית (v1) שיצרתי במהלך הדיון. התיקונים שנעשו בעקבות הדיון בצ'אט:

1. **רכיב 5 חדש** — `activate_trial_with_billing` RPC ל-webhook. v1 הניחה שה-webhook כבר אטומי דרך RPC 0009 הישן. אחרי ה-reset ל-baseline `080d2ee`, ה-RPC הזה נמחק והוויב-הוק חזר להיות לא-אטומי. צריך לבנות מחדש.

2. **CAS guard ב-`activate_trial_with_billing`** — תוקן ל-`status='trial' AND billing_customer_id IS NULL`. v1 הציעה `now() < trial_ends_at`, אבל `trial_ends_at` הוא NULL לפני ה-webhook, אז התנאי היה שובר את ההפעלה.

3. **`pending_billing_sessions` עיצוב פשוט** — v1 הציעה DROP UNIQUE קיים + partial index חדש + שמירת terminal states (`consumed`, `failed`). v2 משתמש ב-UNIQUE הקיים ומוחק terminal states מיד. CHECK של 2 ערכים בלבד.

4. **`has_paid_access` משתמש ב-`add_one_month`** — לא ב-`dateutil.relativedelta`. הפונקציה הקיימת כבר מטפלת ב-edge cases (פברואר, 30 ימים).

5. **`search_path = ''`** עם שמות מלאים — לא `search_path = public`. עקבי עם 0002/0006 ויותר מאובטח.

6. **`REVOKE FROM public` לפני `GRANT`** — קונבנציה זהה ל-0006.

7. **CHECK של status בלי `'pending'`** — `'pending'` הוא ערך של `tier`, לא של `status`. הוסר.
